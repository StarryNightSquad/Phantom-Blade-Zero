## 一、实测数据（这一节是判断依据）

以下数据由脚本直接解析二进制 FBX 与 PNG 得到，不是推测。

### 1.1 骨骼

| 项目 | `Baiyi_Final.fbx`（身体） | `Baiyi_Head.fbx`（头部） |
|---|---|---|
| 骨骼总数 | 1134 | 1134 |
| 骨骼名称集合 | **完全一致** | **完全一致** |
| 前 3 根顺序 | `root, pelvis, spine_01` | `root, ik_weapon_root, ik_weapon_r` |
| `pelvis` 所在索引 | **1** | **16** |
| 几何体数量 | 6（含 3 个多余 Icosphere） | 1 |

> 名称一致、数量一致、**只有顺序不同**。这一条直接解释了"头部固定朝身体右侧"——顶点被错误索引的骨骼驱动，产生固定角度的整体旋转，而不是拉伸或塌陷（拉伸/塌陷才是绑定姿势不一致的特征）。

### 1.2 贴图

| 文件 | 尺寸 | 唯一色数 | 实际值 | 含义 |
|---|---|---|---|---|
| `T_BY_ORM.png` | 256×256 | **1** | (0, 179, 255) | Metallic=0 / Rough=0.70 / AO=1.0 |
| `T_BY_ORM_ARM_backup.png` | 256×256 | 1 | (255, 179, 0) | 另一种打包顺序的备份 |
| `T_BY_FlatNormal.png` | 256×256 | **1** | (128, 128, 255) | **平法线，无任何细节** |
| `T_BY_metal.png` | 256×256 | 1 | (184, 184, 189) | 灰色 albedo 占位 |
| `T_BY_white.png` | 256×256 | 1 | (240, 238, 232) | 白色 albedo 占位 |
| `T_BY_black.png` | 256×256 | 1 | (24, 24, 26) | 黑色 albedo 占位 |
| `T_BWC_*_D.png` × 7 | 1024×1024 | 多 | — | 唯一带真实细节的 albedo |
| `T_Skin_Body_D.png` | 4096×4096 | 多 | — | 身体皮肤 albedo |
| `T_HeadSkin.png` | 2048×2048 | 多 | — | 头部皮肤 albedo |

两点结论：

1. **ORM 是纯色常量图**，它被设计成"全槽统一金属度/粗糙度"。它不可能承载细节，所以"ORM 通道打包错了"这个方向可以彻底关闭。
2. **tex 目录里没有任何 `_N` 法线贴图**。27 个 PNG 中，带实际信息的只有 albedo 系列。法线用的是一张纯色 `(128,128,255)` 占位图 —— 引擎读到的切线空间法线恒为 (0,0,1)，表面光照必然完全平坦。

> 因此"贴图看不出细节"至少有一半来自资产本身缺法线，与材质参数无关。先补 `T_BWC_*_N`，再谈参数。

### 1.3 多余对象

`Baiyi_Final.fbx` 中混入 `Icosphere`、`Icosphere.001`、`Icosphere.002` 三个网格对象（共 6 个 Geometry：3 个 Icosphere + 3 个真实网格）。导入 UE 会额外生成 3 个静态网格资产，建议导出前删除。

## 二、材质不上色

### 2.1 机制

**MaterialInstanceConstant 不生成自己的 shader map，它复用父材质的 shader map。**

父材质若不是游戏 pak 里那一份原始资产，会出现两个后果：

1. **没有可用的 shader map** → 退回默认材质 → 均匀灰、带高光、贴图完全不采样。
2. cook 时写入 MI 的 `FMaterialCachedExpressionData`（参数索引、GUID、覆盖表顺序）是按**本地那份副本**计算的；运行时引擎按**路径**解析到游戏原件，两边元数据对不上 → 参数覆盖被静默丢弃，不报错、不留日志。

这与观察到的现象完全吻合：运行时能查到 MI 类型正确、参数值正确、贴图路径正确，但视觉上就是不上色。

### 2.2 为什么作者的做法有效

作者的流程是「复制游戏自带的 `MI_ZeroHun_Cloth_01_b` → 改名 → 只换贴图」。这不是玄学：

- 父材质 100% 是原件，shader map 一定存在；
- 整张 parameter override 表是从一份**已经被游戏 cook 过**的资产结构拷贝来的，参数名、关联类型、序列化顺序天然对齐；
- 贴图引用按路径解析，改名不影响。

反过来，"从空 MI 新建 + 自建占位母材质 + 逐项填参数"这条路，即使每个参数值肉眼看起来一致，序列化结构也是新的，一旦父材质不是原件就必然失配。

### 2.3 先做二分测试（20 分钟，一次只改一个变量）

用 `tex_test/` 里的图，按顺序做，**不要并行改多个变量**。

| 步骤 | 操作 | 结果 A | 结果 B |
|---|---|---|---|
| 1 | 槽 0 的 Albedo 换成 `T_Test_Red.png` | **变红** → 贴图绑定通路正常，问题只在 ORM/标量，进第 2 步 | **不变红** → 参数覆盖整条链已死，直接跳到 2.4，停止调参 |
| 2 | Albedo 还原，ORM 换成 `T_Test_ORM_NoBlue.png`（B 通道归零） | **金属感消失** → 模板固定把 B 当 Metallic，B=255 就是全金属的源头 | **无变化** → 金属感来自标量参数或母材质默认值 |
| 3 | 对照组：ORM 换 `T_Test_ORM_Neutral.png`（灰 128） | 用于交叉验证第 2 步 | — |

这一步的价值：把"参数问题"和"资产身份问题"彻底分开，避免继续在参数上打转。

### 2.4 修复步骤（复制资产法）

1. 用 FModel 打开游戏 pak，定位 `MI_ZeroHun_Cloth_01_b`（或任一已知显示正常的服装 MI）。
2. 连同它引用的贴图一起导出 `.uasset`（保持 `/Game` 或插件根下的原始路径不变）。
3. 用 UAssetAPI / UAssetGUI 复制该 uasset，改名为你的 MI 名（如 `MI_BY_Coat_01`）。
4. 只允许改这三处：
   - `TextureParameterValues` 中 Albedo / Normal / Mix 的引用，指向你的贴图资产；
   - 若有需要，标量参数按 NOTES 第四节的表微调；
   - **父级（Parent）一个字节都不要动。**
5. 每个材质槽一份，17 槽（身体）+ 10 槽（头部）。
6. 重新 cook 打包，用同一个挂载点覆盖测试。

> 如果第 1 步诊断为"不变红"，这一步是唯一可行路径，没有替代方案。

### 2.5 贴图导入设置（必须与原件一致）

所有源 PNG 都是 RGBA（color type 6，带 alpha 通道）。导入 UE 时按用途分别设置：

| 用途 | sRGB | Compression | Mip Gen | 备注 |
|---|---|---|---|---|
| Albedo（`*_D`） | ✅ 开 | Default (BC1/BC7) | ✅ | alpha 通道若要用于 Masked 裁切，需 BC7 |
| Normal（`*_N`） | ❌ 关 | **Normalmap**（BC5） | ✅ | 若误设为 Default，光照方向全错 |
| ORM / Mask | ❌ 关 | **Masks** 或 BC7 | ✅ | 误开 sRGB 会把 179 解码成 ~0.45，粗糙度直接错 |
| 透明度贴图（`T_BraidOpacity`、`T_HeadLash`） | ❌ 关 | Alpha / BC7 | ✅ | 需与材质的 Masked 设置配套 |

**这一项与"参数值是否正确"无关，但它决定了 shader 采样到什么。** 建议在补法线贴图时一并核对。

## 三、头部朝向错乱

### 3.1 原理

Blender 的顶点权重存放在**顶点组**里，顶点组按**骨骼名字**索引，与骨架的节点顺序无关。

所以修复不是"重算权重"，而是**换骨架容器**：把网格从它自带的那套骨架（顺序错误）挂到顺序正确的那套骨架上。权重自动生效，一个数值都不用改。

权威骨架来源：`Baiyi_Final.fbx` 里的 `Armature`。它的顺序已验证为 `[0]=root, [1]=pelvis, [2]=spine_01`，与游戏 `Hun_Skin_Skeleton` 一致，且身体部分在游戏里实测正常。

### 3.2 操作

1. Blender 打开 `fix_head_rebind.py`，确认 CONFIG 三个路径正确。
2. Run Script。脚本会：
   - 导入 `Baiyi_Final.fbx` 取权威骨架（并警告它里面的多余 Icosphere）；
   - 导入 `Baiyi_Head.fbx` 取头部网格；
   - 记录网格世界矩阵 → 断开原父级 → 删除指向旧骨架的 Armature 修改器；
   - 检查顶点组：能映射到权威骨架的保留，映射不到的直接删除并报告；
   - 挂到权威骨架 + 重建 Armature 修改器（`use_vertex_groups=True`）；
   - 统计零权重顶点、最大影响骨骼数（>8 会警告）；
   - 删除旧骨架，只导出「头部网格 + 权威骨架」。
3. 导出参数已固定为与原文件一致：`axis_forward='Y'`、`axis_up='Z'`、`apply_scale_options='FBX_SCALE_ALL'`、`add_leaf_bones=False`。**不要改动这几项**，否则进 UE 会额外变形。

### 3.3 验证（不用开 UE）

```bash
python check_fbx_bones.py Baiyi_Final.fbx Baiyi_Head_fixed.fbx
```

- 输出 `✅ 骨骼名称与顺序完全一致` → 可以进 UE
- 输出 `❌ 第 N 根开始顺序不一致` → 不要进引擎，先查脚本是否真的替换了骨架容器

这条循环是秒级的，替代了"导入游戏看效果"的试错方式。

### 3.4 UE 内验收标准

导入后必须逐项确认，任一不符都会重现朝向问题：

- `SkeletalMesh.Skeleton` 的资产路径是插件根：`/HuaShira/Characters/Hero/Hero_Hun/Hun_Skin_Skeleton`
- **不是** `/Game/HuaShira/...`（插件内容用 `EditorAssetLibrary.load_asset` 会返回 None，导致 UE 自动新建一个 `_Skeleton`）
- `ReferenceSkeleton` 为 **1134 根**
- 第 0 根是 `root`，第 1 根是 `pelvis`

## 四、前臂少一节 【⚠️ 已失效】

> **当前采用 rigid 模式（顶点位置完全不动，只 ×100 换算单位），"从肘到腕搬权重会丢一节"这个问题不复存在。**
> 以下内容是上一轮「逐骨相似变换」方案下的补救记录，仅作历史参考。



现有做法是"肘→腕相似变换搬权重"，这个思路本身不可靠：相似变换只保证骨骼变换的相似性，无法还原逐顶点的多骨混合权重，一旦跨越关节就会丢一节。

两种可靠替代：

1. **按骨骼名复制顶点组**（首选）：从女眷原手部网格直接复制同名顶点组权重到新网格，名字对上即可，不需要空间计算。
2. **空间权重转移**：用 `blender_outfit_port.py` 的 Data Transfer（`POLYINTERP_NEAREST`，`layers_vgroup_select_dst='NAME'`）从原手臂网格传权重。

转移后必须做三步清理：去零权重 → 限制影响骨骼数 ≤8 → 重新归一化（脚本已内置）。

## 五、鞋底再抬 5mm 【⚠️ 当前未执行】

> 当前交付的 FBX **没有做任何抬高**，鞋底高度交由封包侧按外观表/胶囊体统一处理。



**不要动网格。** 单独抬高鞋底会把脚踝处的顶点关系撕开，出现缝隙；整体抬高又会连带整个人物。

正确做法按优先级：

1. 改 `DT_PBZAppearanceTable` 中 Body 行对应的偏移/位置字段（如果有）；
2. 改 root 骨的相对位移；
3. 若游戏用 Appearance 系统的胶囊体高度做落地对齐，改胶囊体而不是网格。
